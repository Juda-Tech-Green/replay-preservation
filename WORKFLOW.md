# Recovery and validation workflow

Use a new disc identity and new run directories for every medium/attempt. Keep English infrastructure and original software names/content. A successful stage is evidence for that stage only.

1. **Intake and authorization.** Record label, operator observations, device/mount identity and physical condition. Cracks, warping or unusual noise/vibration stop physical reads. Define acquisition scope, geometry, retries and stopping limits separately; an earlier disc's authorization does not transfer. Never infer physical safety from hashes.
2. **Acquisition.** In an explicitly approved environment, retain exact command/tool version, tracks/sessions, start/end timestamps, expected size, source identification, logs and original ddrescue map. Read-only mounted-file assessment is a separate operation and cannot substitute for track-aware acquisition. Stop at approved error/time boundaries. Baseline v0.1 does not run acquisition.
3. **Artifact verification.** Preserve originals; hash local regular working copies and compare expected digests. Parse the map with expected acquisition domain. Keep `?`, `*`, `/`, `-` and unmapped regions separate. Unknown geometry or unavailable source files blocks downstream claims.
4. **Filesystem and extent assessment.** Choose ISO9660/Joliet explicitly. Gate metadata and payload reads on map `+`, allocated bytes and EOF. Retain parse errors, raw recording timestamps, namespace, multi-extent provenance and layout warnings. Do not treat zero bytes as either proof of corruption or proof of recovery. Do not infer authentic data from sparse holes. Unknown layouts remain unknown.
5. **Target planning and handoff.** Rank package benefit from actual missing allocated ranges; distinguish known failures from untried spans and deduplicate shared extents. Prepare exact sector intervals, not broad directory envelopes. Future reads require fresh specific authorization. A target map records absolute input offsets even when chunk output starts at zero. Validate expected chunk/map hashes and the full authorized interval before merging.
6. **Derivative reconstruction.** Produce new image/map pairs. Copy only verified recovered spans, reject conflicting `+` overlaps, translate chunk-local offsets to absolute disc coordinates, verify imported bytes, and rehash inputs/outputs. Failed derivatives stay labeled unusable. Never patch an original or promote an unrecovered hole.
7. **Extraction and static validation.** Extract only fully sector-covered known packages, preserving filenames. Check each output length and SHA-256 against image extents; retain roles, formats, dependencies and uncertainty. MZ/WAD structural checks establish bounded properties only. Deep archive checks require verified working copies, separate limits and supported parsers. A known 15-file set is not proof of every possible runtime dependency.
8. **Emulation preparation.** Select an emulator based on actual headers/runtime needs. Review installed version, private filesystem/network/device/display boundaries, resource limits, bounded output, authenticated viewer/input protocol and cleanup. Test the boundary with harmless software first. Installation, recovered execution and retries each need their applicable scope; the baseline skill grants none.
9. **Supervised execution.** Only after a fresh explicit authorization, launch the approved disposable package once with the exact reviewed launcher. Preserve wall time and CPU as distinct limits. Human controls the game. Record menu/transition markers and screenshots contemporaneously, per-control confirmations, errors and exit reason. For DOOM II, instruct physical **Pause/Break**, not P. Confirm save and multiplayer non-use separately; avoid historical saves and utilities when excluded. See `templates/supervised_session.json` for a future proposal, not an authorization.
10. **Close and seal.** Verify termination and process/IPC cleanup, preservation hashes and output bounds. Keep raw UI results and later human clarifications separately. Missing timestamps stay null; a post-game frame is not a gameplay capture. A supervisor deadline does not establish a crash. Append a scoped compatibility observation while retaining previous results and source coverage/integrity distinctions. Seal reports and catalog snapshot with a manifest; review publication rights and private paths before any export.

The public offline CLI supports artifact/extent analysis, derivation, extraction and static checks, plus offline session review. It never launches an emulator or performs acquisition. Historical private orchestration scripts are excluded. Lower-level developer APIs for mounted assessment or catalog writing have different effects and must not be used on evidence that must remain immutable.

For regression work, use generated ISO, MZ/WAD and compact chunks under temporary directories. `tests/fixtures/disc01_cases.json` contains metadata only. Do not substitute proprietary game bytes into tests. Run `.venv/bin/python -m unittest discover -s tests -v`; two existing ddrescue tests use synthetic regular files only and skip when ddrescue is unavailable.
